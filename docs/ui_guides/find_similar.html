Find Similar Neurons

Search for neurons similar to a query by morphology (skeleton shape) or by connection profile (synaptic partner structure). A mode toggle switches between the two search families.

Morphological similarity

Two methods are available. Both reuse the skeleton/mesh data cached under cache/{dataset}/skeletons/ (including nested bulk folders); the query neuron's skeleton is fetched on demand if missing.

MethodCostNotes
Vector (recommended)<10 ms per query Each neuron is reduced to ~24 morphometrics plus a 100-dim shape block: a persistence vector for skeletons, a spatial histogram for meshes (FlyWire bulk caches). Scores are cosine / Pearson on z-scored vectors. Requires the skeleton vector cache (auto-built on first query, or use the Build Vector Cache button).
NBLAST~5–15 s for 100 prefiltered candidates Canonical Costa et al. 2016 pairwise score via navis, on skeletons only (FlyWire mesh caches do not support NBLAST — use the vector method there). Dotprops are rebuilt per query and never cached.

Candidate source

Level controls the result granularity. auto (default) follows the query kind: a type query returns type-to-type rows (each row = one target type), a bodyId query returns bodyId-to-bodyId rows. bodyid/type force a level for multi-neuron or mixed queries.

Candidate Source selects how candidates are discovered before morphological scoring:

  • auto (default): NeuPrint datasets (hemibrain, male-cns, ...) use the connectivity-expanded search: candidates are found directly in the connection cache (cache/{dataset}/connections.parquet — neurons sharing upstream/downstream partners with the query, ranked by shared-partner count), the top N × Candidate Expansion connectivity-similar types are kept and expanded to all their member neurons; skeletons are then fetched for the pool (transient) and morphology is compared. FlyWire datasets (which have bulk mesh caches) search the vector cache directly (full-morphology). All scores are computed at one consistent representation level: skeleton and mesh neurons (or two simplification levels) are never mixed in a single comparison — neurons cached or fetched at a different level than the query are simply not scored.
  • profile: always connectivity-expanded (all datasets).
  • cache: full-morphology over the complete local skeleton population (download skeletons first — see below).

Candidate Expansion (×) (default 3) controls the type-level expansion: with top_n=10 the top 30 connectivity-similar types are kept and every member of those types enters the scoring pool (per-type safety cap 100). Fetched skeletons are transient by default — used for the current comparison only and never written to the skeleton cache; the Cache Fetched Skeletons option saves them to the local cache for reuse (for a persistent full-morphology pool prefer Download All Skeletons). Either way the computed vectors are always persisted into the vector cache — the lookup order is vector cache, then cached skeleton file, then online fetch, and a fetched neuron is never vectorized twice. Already-cached skeletons are reused and the query neuron is always fetched if missing. ROI Filter (shown when the dataset's connection cache carries synapse location data — male-cns has 114 ROIs like AL(L), hemibrain has none) restricts candidate discovery to synapse rows in the selected ROIs. Results carry both profile_similarity (normalized shared-partner count) and similarity (morphology) scores. If no candidates are found, the search falls back to the vector cache when available.

Full-morphology mode & skeleton download

Download All Skeletons fetches every missing skeleton of the dataset to cache/{dataset}/skeletons/ — the same resumable background-pull pattern as the Settings panel's full dataset pull (parallel, progress bar with ETA, cancel; already-cached skeletons are skipped). FlyWire FAFB v783 already has bulk skeletons locally, so only the vector cache build is needed there. After the download, build the vector cache and run with Candidate Source = cache to compare the query against the entire local skeleton population (fully morphology-based analysis).

Skeleton vector cache

One parquet file per dataset: cache/{dataset}/morphology/skeleton_vectors.parquet (~1 KB/neuron, ~30–50x smaller than the raw skeletons). It builds incrementally from already-cached skeletons (~15–85 ms/neuron) and is auto-triggered on the first query. Without a vector cache, the connectivity-expanded search z-scores the pool vectors with pool-computed statistics so cosine scores stay scale-fair.

Connection profile similarity

The relocated "find similar" search from Homolog Finding: query-vs-all within one dataset (default) or across datasets, ranked by connectivity profile similarity. Same backend (HomologFinder) and the same loose-search knobs:

  • Min Shared Partners (default 2): shared partners required for a candidate; 1 = loosest discovery.
  • Candidate Prune % (default 5): top N% of cosine-positive candidates kept after vector pre-filtering; 100 = keep all (loosest).
  • Fast Search (default on): adjacency expansion; switch off for the comprehensive query-vs-all search.

Results are additionally enriched with vector-based morphological similarity columns (morph_cosine, morph_pearson) computed from the final ranked rows only.

Intra-type reference data

Every search reports the query's intra-type similarity alongside the inter-type rows, so results are always comparable against a same-type baseline:

  • Type queries return the query type itself as the first row (is_intra_type=True). Its similarity is the type's cohesion (mean score of its members against the query vector) and intra_type_similarity is the mean pairwise similarity of the type's members — the intra-type reference every other row is ranked against. n_bodyids gives the member count.
  • bodyId queries tag same-type hits with is_same_type=True and carry the query type's intra_type_similarity on every result row.

In practice (hemibrain v1.2.1, verified 2026-08): aMe12's two members are each other's top hit (0.90 = the intra-type similarity), aMe5 bodyId queries return 10+ same-type members before any inter-type row, and sim(aMe12, aMe10) > sim(aMe12, aMe5) in both directions. Note that single-cell types (e.g. SMP581) can tie or exceed the cohesion of morphologically diffuse types (aMe10, aMe5) — the intra row is a reference, not a guaranteed winner.

3D visualization of the found neurons

After a morphological run, the top-N types of the found similar neurons can be rendered as an interactive 3D skeleton view (same engine as the 3D Skeleton tab and the NeuronBridge FindNeuron visualization):

  • Visualize Top-N Types (default 6; 0 = disabled): number of top result types/rows to render.
  • Visualize By (default type): type renders one layer per top type, containing all of its member skeletons found in the results (type-level queries resolve members from the vector cache, bounded by BodyIds / Type); bodyId renders one layer per top result neuron.

Each layer is colored per type and labeled r{rank}_{type}_x{N} (rank = similarity rank of the type, N = member count). The intra-type reference row is never rendered. The interactive HTML is saved next to the results in {run_folder}/plot3d_{dataset}/ and listed in the output panel; a visualization failure never discards the search results.

Output

Each run is saved in its own timestamped folder with two always-written result tables (mirroring the homolog finding outputs):

morphological: {output_dir}/findsimilar_{DATASET}_{query}_{timestamp}/
                 results.csv, type_summary.csv, README.txt
profile:       {output_dir}/findhomologs_{SRC}_to_{TGT}_{query}_{timestamp}/
  • results.csv always holds bodyId-level similarities (ranked target_bodyId rows), whatever the query kind. A type query ranks the individual neurons of the found types; the query type's own members are excluded.
  • type_summary.csv always holds type-level similarities (one row per target type, the query type first as the intra-type reference with is_intra_type=True), whatever the query kind. Type searches rank the top-N types over the whole cached skeleton population (connection candidates + cached skeletons), so the result is not capped at the candidate types.
