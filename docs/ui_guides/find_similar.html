Find Similar Neurons

Search for neurons similar to a query by morphology (skeleton shape) or by connection profile (synaptic partner structure). A mode toggle switches between the two search families.

Morphological similarity

Two methods are available. Find Similar uses raw skeletons only. Raw skeletons are shared at cache/{dataset}/skeletons/raw_skeletons/; Find Similar's vector parquet remains under cache/{dataset}/find_similar/. The visualization simp90 cache is never used for comparison.

MethodCostNotes
Vector (recommended)<10 ms per query Each neuron is reduced to ~24 morphometrics plus a 100-dim shape block: a persistence vector for raw skeletons. Scores are cosine / Pearson on z-scored vectors. Raw vector rows are cached at find_similar/morphology/skeleton_vectors.parquet; if a row is missing it is fetched online and vectorized.
NBLAST~5–15 s for 100 prefiltered candidates Canonical Costa et al. 2016 pairwise score via navis on raw skeletons only. Dotprops are rebuilt per query and not persisted.

Dotprops were benchmarked on the 8,839-node raw aMe12 skeleton: building them with k=20 took about 28 ms, while a compressed serialized dotprops object was about 144 KB. A compressed raw skeleton was about 48 KB in the same benchmark, so dotprops caching would use more space while saving only tens of milliseconds per neuron. It is not enabled by default. NBLAST score caching was evaluated separately. A final pair-score cache would need a dataset revision, ordered bodyId pair, navis/NBLAST version, dotprop parameters, scale and scoring options in its key. In practice the reusable cost is raw skeleton/vector preparation; the current design keeps those assets and recomputes dotprops/scores so stale scores cannot survive a dataset or parameter change.

Candidate source

Level controls the result granularity. auto (default) follows the query kind: a type query returns type-to-type rows (each row = one target type), a bodyId query returns bodyId-to-bodyId rows. bodyid/type force a level for multi-neuron or mixed queries.

Candidate Source selects how candidates are discovered before morphological scoring:

  • auto (default): NeuPrint datasets (hemibrain, male-cns, ...) use the ROI-distribution screen: every neuron of the dataset is ranked by cosine similarity of its input/output synapse distributions over the dataset's primary ROIs (from {dataset}_allneurons_roi_count_df.parquet, or the legacy CSV from older pulls), comparing both orientations across the midline (bilateral mirror) so contralateral homologs match. This reaches every neuron — the connectivity screen below can never find neurons without shared partners (~8% of same-type members on male-cns). A one-time per-dataset matrix is cached (cache/{dataset}/morphology/roi_profiles.npz); the top screen-ranked types (bounded by Candidate Cap) are kept and expanded to all their member neurons; raw skeletons are then fetched for the pool and shared for reuse. FlyWire/FAFB sources use healed raw skeletons or the CAVE fallback. Mesh and simp90 visualization files are never candidates for either method.
  • roi: the ROI-distribution screen only. Requires the dataset's ROI-count table and metadata sidecar (missing sidecars are fetched and saved once automatically).
  • combined: union of the ROI screen and the connectivity (shared-partner) screen — the widest candidate pool and the highest recall per fetched skeleton, at the cost of more transient skeleton fetches.
  • profile: the connectivity screen only — candidates found directly in the connection cache (cache/{dataset}/connections.parquet: neurons sharing upstream/downstream partners with the query, ranked by shared-partner count).
  • cache: full-morphology over the complete local raw skeleton population (download raw skeletons first — see below).

Candidate Cap (default 500) is the single knob bounding how many candidates are ever compared: the sorted candidate list of the selected screen is truncated to this many neurons, which become the scoring pool (it also serves as the NBLAST prefilter of cache-mode searches; pure cache vector searches compare the whole local population). Fetched raw skeletons are always persisted as portable .swc.gz files in the shared dataset cache at skeletons/raw_skeletons/ for reuse by every workflow. The computed raw vectors are persisted into the vector cache — the lookup order is vector cache, shared raw skeleton file, then online fetch, and a fetched neuron is never vectorized twice. Already-cached raw skeletons are reused and the query neuron is fetched if missing. ROI Filter (shown when the dataset's connection cache carries synapse location data — male-cns has 114 ROIs like AL(L), hemibrain has none) restricts the candidate rows of the connectivity screen (roi/combined discovery is dataset-wide by design). results.csv and type_summary.csv contain ALL compared candidates (bounded by the cap), each row carrying the screen evidence — roi_similarity (primary-ROI distribution cosine) and/or profile_similarity (normalized shared-partner count) — alongside similarity (morphology); Top N applies to the optional 3D visualization only. If no candidates are found, the search falls back to the vector cache when available.

Full-morphology mode & skeleton download

Use Settings → Dataset Cache → Download All Skeletons to download a complete raw skeleton population. The button sits beside Pull Complete Connections, before Cancel. New bulk files use portable {bodyId}.swc.gz; older pickle files remain readable. Both the download and vector-cache update are resumable. After a raw download, build the vector cache and run with Candidate Source = cache to compare the query against the entire local skeleton population. The healed FAFB skeleton bundle remains a local raw source and is vectorized without copying its SWC entries.

Skeleton vector cache

One raw parquet file per dataset: cache/{dataset}/find_similar/morphology/skeleton_vectors.parquet (~1 KB/neuron, ~30–50x smaller than the raw skeletons). It builds incrementally from already-cached skeletons (~15–85 ms/neuron) and is auto-triggered on the first query. Without a vector cache, the connectivity-expanded search z-scores the pool vectors with pool-computed statistics so cosine scores stay scale-fair.

Connection profile similarity

The relocated "find similar" search from Homolog Finding: query-vs-all within one dataset (source and target dataset are the same), ranked by connectivity profile similarity. Same backend (HomologFinder) and the same loose-search knobs:

  • Min Shared Partners (default 2): shared partners required for a candidate; 1 = loosest discovery.
  • Candidate Prune % (default 5): top N% of cosine-positive candidates kept after vector pre-filtering; 100 = keep all (loosest).
  • Fast Search (default on): adjacency expansion; switch off for the comprehensive query-vs-all search.

Results are additionally enriched with vector-based morphological similarity columns (morph_cosine, morph_pearson) computed from the final ranked rows only.

Similarity score formulas (connectivity)

Let A and B be the two connectivity profiles (each a dict of partner type → weight, restricted to the top-K partners per direction), and let ρ denote the Spearman rank correlation of two weight vectors. All metrics are always computed for every pair; the Sort By metric only selects the ranking cutoff. Rank correlations are reported raw (−1 to 1); there is no normalized 0–1 variant and no combined score.

ScoreFormulaRange
jaccard|A ∩ B| / |A ∪ B| (partner-type sets)0–1
weighted_jaccardΣ min(w_a, w_b) / Σ max(w_a, w_b) over the partner-type union0–1
cosine(A·B) / (‖A‖·‖B‖) over the union (missing partners = 0)0–1
rank_corrρ = Spearman(w_a, w_b) on shared partners (NaN if < 3 shared)−1 to 1
rank_unionρ computed over the union of both partner sets (missing = 0)−1 to 1
shared_type_count|A ∩ B|integer
union_type_count|A ∪ B|integer
adjacency_scoreshared-partner (synaptic-contact) count used for adjacency expansioninteger
morph_cosine(A·B) / (‖A‖·‖B‖) on z-scored morphology vectors (enrichment)0–1
morph_pearsoncosine of the mean-centered morphology vectors (enrichment)−1 to 1

The direction of a direction-aware comparison (upstream, downstream) is computed per direction and then averaged for both; rank metrics use the min_partners threshold (default 5) and return NaN when the partner set is too small to correlate.

Similarity score formulas (morphology)

The three evidence columns are computed independently and are never mixed across candidate sources; the primary similarity column is the morphology score only.

ScoreFormulaRange
similarityvector: cosine or Pearson of z-scored vectors (see metric); NBLAST: normalized pair score0–1
roi_similaritycosine of input/output synapse-distribution vectors over the primary ROIs, mirrored across the midline0–1
profile_similarityshared-count / max-shared-count (normalized shared-partner count)0–1
intra_type_similaritymean pairwise similarity of the type's members (the intra-type reference)0–1

For the vector method, each neuron is reduced to ~24 morphometrics plus a 100-dim persistence block; the pool is z-scored with pool-computed statistics so cosine scores stay scale-fair.

Intra-type reference data

Every search reports the query's intra-type similarity alongside the inter-type rows, so results are always comparable against a same-type baseline:

  • Type queries return the query type itself as the first row (is_intra_type=True). Its similarity is the type's cohesion (mean score of its members against the query vector) and intra_type_similarity is the mean pairwise similarity of the type's members — the intra-type reference every other row is ranked against. n_bodyids gives the member count.
  • bodyId queries tag same-type hits with is_same_type=True and carry the query type's intra_type_similarity on every result row.

In practice (hemibrain v1.2.1, verified 2026-08): aMe12's two members are each other's top hit (0.90 = the intra-type similarity), aMe5 bodyId queries return 10+ same-type members before any inter-type row, and sim(aMe12, aMe10) > sim(aMe12, aMe5) in both directions. Note that single-cell types (e.g. SMP581) can tie or exceed the cohesion of morphologically diffuse types (aMe10, aMe5) — the intra row is a reference, not a guaranteed winner.

3D visualization of the found neurons

Both similarity modes can render the query and found neurons as interactive 3D skeleton views (same engine as the 3D Skeleton tab and the NeuronBridge FindNeuron visualization). Each mode has its own visualization list and settings, so morphological results and connectivity results are never mixed.

  • Morphological — Visualize Top N Types / Neurons (default 10; 0 = disabled): number of top morphology result types/rows to render.
  • Connectivity — Visualize Top N Candidates (default 5; 0 = disabled): number of top connectivity-similar candidates to render. The query is included as the first reference layer, so the scene contains query + top-N candidates.
  • Visualize By (default type) applies independently within each mode: type renders one layer per top type, containing all of its member skeletons found in the results (type-level queries resolve members from the vector cache, bounded by BodyIds / Type); bodyId renders one layer per top result neuron.
Analysis-tab visualizations default to Skeleton Mode = line for speed. For high-quality morphology, open Visualization → Skeleton, or change the mode to tube and choose fine with 95% simplification.

When multiple queries are entered, the tab runs them sequentially and saves each query in its own run folder. Morphological output is saved next to its results in {run_folder}/plot-3d_{ABBREV}_{dataset_folder}/. Connectivity output is saved in separate visualization/bodyId_level/, visualization/type_level/, and visualization/source_neurons/ folders. Each scene starts with a query reference layer, followed by up to the requested top-N result layers. Each layer is colored per type and labeled r{rank}_{type}_x{N} (rank = similarity rank of the type, N = member count). The intra-type reference row is never rendered. The interactive HTML files are listed in the output panel; a visualization failure never discards the search results.

Output

Each run is saved in its own timestamped folder with two always-written result tables:

                 results.csv, type_summary.csv, README.txt

                 results/

                   intra_type_results.csv          # same-dataset searches
                   source_status_summary.json
                 profiles/query/..., profiles/matches/...
                 overlaps/{source}_vs_{target}.csv
  • results.csv always holds bodyId-level similarities (ranked target_bodyId rows), whatever the query kind. A type query includes unique intra-type bodyId pairs for every resolved query member, followed by the top inter-type bodyId rows.
  • type_summary.csv always holds type-level similarities (one row per target type, the query type first as the intra-type reference with is_intra_type=True), whatever the query kind. Type searches rank the top-N types over the whole cached skeleton population (connection candidates + cached skeletons), so the result is not capped at the candidate types.
Exported run guide: every successful run also writes _UserGuide_please_read_me.html into the run folder — a self-contained explanation of every output file, every table column, and any warnings recorded for the run. Format (html / txt / markdown / disabled) is set in Settings → Default Settings → Run Guide Format.
