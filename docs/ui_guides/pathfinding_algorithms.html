Pathfinding Algorithms

How DROCAT finds multi-hop pathways and which algorithm to pick. Linked from the Algorithm selector in Find All Paths and the Pathfinding Algorithm selector in Cross-Dataset Comparison.

What "pathfinding" means here

Given a set of source neurons and a set of target neurons, DROCAT enumerates every acyclic connection chain (path) from any source to any target with at most Max Intermediate Layers + 1 edges (the cutoff). All five algorithms return exactly the same paths — they only differ in how fast they run and how much memory they use.

Path counting is exponential in the cutoff (each extra hop multiplies the search by the average branching factor), so the algorithm choice matters most for deep queries (3+ intermediate layers) on dense connectomes.

The algorithms

DP (Backward Reachability)

First computes which nodes can reach a target within the cutoff (backward DP layers), then runs a forward search that only follows edges that provably lead to a target.

Strongest dead-end pruning; stores only node sets. Fastest measured at 3 intermediate layers (0.02 s) with low, flat memory. Degrades on very deep (5+) queries. Not the default — MemoizedDFS is.

DFS (Backward Memoized)

A standard depth-first traversal from the targets, remembering which nodes can still reach a source at each remaining depth.

Moderate memory. Fastest at 4 intermediate layers and the best time-memory tradeoff at 5, when the target group is small (the backward direction starts from the smaller set).

Best for: deep paths with few targets.

MemoizedDFS (Forward Memoized)

A depth-first traversal from the sources that remembers which successors can still reach a target at each remaining depth, so each (node, depth) state is computed once.

Moderate memory and no reversed-graph copy — the memo is built from the sources and pruned to successors that can reach a target, so the search stays inside the source-side cone. Fastest at 4 intermediate layers; the default.

Best for: balanced queries; deep paths with many targets.

MeetInMiddle (Meet-in-the-Middle)

Stores all half-paths up to the middle depth from the sources, then walks backward from the targets and stitches matching halves.

Fastest at shallow depths (2–3 layers), but its half-path table is rebuilt for every length and the pairwise stitching costs more than a fully-pruned shared memo on real connectomes — so it is not the deep-path winner its design suggests.

Best for: shallow queries; a safe middle ground at 4+ layers.

Bidirectional (BFS)

Searches forward from sources and backward from targets at the same time, then stitches the two half-trees at the middle layer.

Shortest paths first. Highest memory: stores the full search trees from both sides, and memory grows with the cutoff (452 MB at 4 layers, 1.1 GB at 5 on a small query). The extra memory buys a smaller search frontier, but not faster enumeration: its path stitching copies lists at every depth and builds sets per candidate pair, so it is the most expensive per path of all four (measured 10.4 µs/path vs 1.8 for DFS/DP on a controlled graph) — the classic bidirectional win only applies to shortest-path search, where you can stop at the first meeting.

Best for: shallow queries where you want shortest paths first and memory is not a concern.

Which one should I pick?

Few targets, many sourcesDFS — the same memoized search started from the smaller (target) side

Practical tips

  • Prefilter the graph: raising Min Synapse Count and lowering Edge Limit – BodyIds shrinks the search space far more than any algorithm choice.
  • Deep + dense = expensive: the number of paths grows exponentially with Max Intermediate Layers; the output itself dominates runtime and memory once path counts reach millions.
  • All algorithms are equivalent: results never depend on the selection — switch algorithms freely to tune speed or memory.
