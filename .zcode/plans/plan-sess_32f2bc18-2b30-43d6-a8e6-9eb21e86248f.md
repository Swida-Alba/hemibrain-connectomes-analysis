# Remove `*_merged_connections.csv` (FlyWire local preparation)

## Answer to your question first

The CSV is **not** only a fallback — it is written by both converters alongside the parquet, and it is the **primary read source** for the core engine:

- `fafb_utils.prepare_fafb_data` (`src/fafb_utils.py:33-39`) returns the merged **CSV** and never looks at the parquet. Everything downstream inherits this: `coana._fetch_connections_bulk` (`src/coana.py:5975-5989`, feeds `build_connection_cache` → the UI dataset-pull), the local fetch path (`src/coana.py:4540-4559`), and `statvis`'s FAFB `getNeurons` (needs `prepare_fafb_data` to succeed to take the fast path).
- `coana._load_connection_db` (`src/coana.py:2691-2712`) imports from `*_merged_connections.csv` (glob) only when the cache parquet is missing.
- Only the comparison modules (`connectivity_profiler`, `comparison_analyzer`) and the UI readiness glob are already parquet-first with CSV fallback.
- The raw `downloads/*.csv.gz` files are absent locally, so deleting the CSVs without switching these readers would break FAFB/BANC.

Good news: both converters store `bodyId_pre/bodyId_post` as **strings** in the parquet (identical semantics to the CSV), so the switch is behavior-neutral.

Space to save: FAFB v783 874 MB + BANC v888 145 MB + BANC v626 135 MB ≈ **1.15 GB** (parquet siblings already exist for all three).

## Changes

1. **`src/fafb_utils.py`** — `prepare_fafb_data`: resolve the merged conn file as `.parquet` if present, else `.csv`; keep the neuron-CSV requirement and legacy downloads path unchanged.

2. **`src/coana.py`**
   - New module-level helper `load_flywire_merged_connections(conn_file)` → DataFrame with `bodyId_pre/bodyId_post` (cast to str) / `weight` (+`roi`), reading parquet or CSV. Use it at both call sites: `_fetch_connections_bulk` (~5981) and the local fetch path (~4553), keeping each site's mtime/memory caching.
   - `_load_connection_db` flywire import (~2694-2712): glob `*_merged_connections.parquet` first, `*_merged_connections.csv` fallback; `pl.read_parquet` vs `pl.read_csv` (the existing Utf8 casts normalize dtypes either way).

3. **Stop exporting the CSV**
   - `src/FAFB_file_converter.py`: remove the `save_csv_path` parameter + CSV write block from `process_connections_to_parquet` (lines 234-236); drop `conn_csv` from `ensure_flywire_data` (lines 542-543, 602).
   - `src/BANC_file_converter.py`: same removals (lines 138-140, 217-218, 247).
   - Neuron-df CSV export stays (different file, still consumed, out of scope).
   - Note: both converters short-circuit when the parquet already exists, so re-running preparation never recreates the CSV.

4. **Delete the three local CSVs** (~1.15 GB freed).

5. **Tests** — new `tests/core/test_flywire_merged_connections.py`: (a) `prepare_fafb_data` prefers the parquet, falls back to CSV; (b) `process_connections_to_parquet` (FAFB + BANC) writes only the parquet on a tiny gz fixture; (c) `load_flywire_merged_connections` returns str IDs from a parquet fixture. Existing readiness tests already touch the `.parquet` name — unchanged.

6. **Docs/UI strings** — drop "(and CSV)" from `ui/tabs/settings.py` (~510, 537), `docs/ui_guides/settings.html`, `skills/drocat-usage/references/datasets-and-auth.md`.

## Verification
- `pytest tests/core tests/ui` (full suite).
- On the real datasets after CSV deletion: `prepare_fafb_data` returns the parquet; `load_flywire_merged_connections` loads FAFB v783 with string bodyIds and the expected row/column shape; converters report "existing converted file found" without regenerating anything.

## Risks
- Machines with only a legacy CSV (no parquet): all readers keep CSV fallback; converter re-run writes parquet only, and the old CSV keeps working until manually deleted.
- Dtype semantics unchanged (IDs stored/read as strings in both formats).
